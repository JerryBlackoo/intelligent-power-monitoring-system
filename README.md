# 基于边缘设备与工业相机的智能电力巡检系统

> 人工智能电力系统应用实训指导

## 关于本仓库

本仓库的 `main` 分支只保留这一份实验指导，不把我们的完整工程当作可直接运行的模板，也不提供可以原样提交的课程答案。课程真正要练的，仍是任务定义、数据治理、实验设计、接口契约、硬件调试、性能测量和结果解释——生成式人工智能可以辅助编码，但不能替代这些环节。

如果有同学想对照我们当时具体是怎么搭的，可以看 [`source` 分支](https://github.com/JerryBlackoo/intelligent-power-monitoring-system/tree/source)。那里归档了我们当时的代码，方便理解模块拆分和联调痕迹；请不要整仓复制后当作自己的交付，也要注意其中可能绑着个人路径、临时公网地址和演示数据。

### 我们对自己工作的复盘

说直接一点：**我们当时投入不够，很多环节并没有做到位。** `source` 可以参考局部想法，但绝不是“标准答案”，更不要照着我们的完成度去估自己该做成什么样。

主要不足有三类：

1. **模型训练意图不清楚。** 最终只落了两个检测模型，类别又铺得很宽；组内对“到底在检测什么、为什么这样拆、验收看哪一类召回”缺少事先对齐。结果是总体数字偶尔还能看，弱类漏检却很严重——这不是再换一个模型名就能解决的，根子在任务定义和数据与评测设计。
2. **系统没有真正对接好。** 边端、云端、前端、相机各自推进时契约不硬；有的同学更倾向于把自己那一块“水过去”，例如相机侧停留在从设备导出几张图，而没有把连续取流、稳定会话和推理上传做成一条可验收链路。页面和接口看起来有了，端到端证据却薄。
3. **真实相机链路做得不扎实。** 课上相机在板端通常是标准 **UVC** 设备；正常做法是用 **UVC + V4L2/OpenCV（或 FFmpeg）** 维持连续视频流，再从最新帧里周期抽帧推理。我们实际没有做成这条视频流链路，更多是每次手动抓一张图再上传/推理，等于把“持续巡检”做成了“单次拍图”，预览、抽帧解耦和稳定性都谈不上；Mock 与真实结果区分不清是叠加问题。

也有一点可以看一看：我们把**小智同学（小智 MCP 工具）接到了巡检系统**上，用来查询状态、辅助说明和建议。若你想做语音/MCP 与业务系统的结合，`source` 里这一块比“整仓照抄模型与相机链路”更值得翻。

### 建议对照：EdgeEye

同课程另一组的 [EdgeEye](https://github.com/L-1ngg/EdgeEye) 在我们看来做得明显更扎实，**非常适合作为实现参考**（同样请带着批判去看，不要无脑 fork）：

- **训练侧思路更清楚**：类别范围收得更紧，数据集来源、清洗报告、训练/导出/校验脚本和实验记录更完整，看得出“先定义任务再训练”。
- **系统侧闭环更完整**：边缘推理、后端契约（含 OpenAPI）、前端仪表盘、故障与报告串在一起，联调边界写得更清楚，而不是各做各的然后临近验收硬拼。

### 一个可选的数据与题目方向

如果老师提供了**无人机**，很值得用它去采集**本校楼顶光伏板**画面，再围绕少数肉眼可见的故障（如脏污、破损、遮挡）做检测或分类。相对只靠网络数据集，这样更容易拿到与验收相机域一致的本域数据，也比一次铺很多无关类别更贴近“先做窄而真的闭环”。飞行与登顶务必遵守学校和指导老师的安全与审批要求；故障样本优先用安全替代或经批准的现场状况，不要自行破坏设备。

阅读建议很简单：用本仓库 `main` 弄清**验收标准和方法**；需要具体工程样例时优先看 **EdgeEye**；要看我们踩过的坑和 MCP 结合时再翻 **`source`**。后面章节里的“应当继承 / 不应照抄”，很大程度上就是对着我们这些不足写的。

本指南来自对我们原型的复盘，并对照了做得更好的同学实现。`main` 保留可迁移的方法与验收标准；`source` 保留我们当时的具体代码，方便查阅。

## 一、课程目标

本课程的目标不是做一个界面看起来完整的监控大屏，而是完成一条有证据、可复现、可测量的真实链路：

**工业相机持续采集画面，边缘设备按设定周期选取最新帧并运行真实模型，云端保存证据和结构化结果，前端同步展示设备状态、识别结果、历史事件与性能数据。**

最终系统至少应做到：

1. 使用老师提供的工业级摄像头持续获得稳定画面，而不是只读取演示图片。
2. 在目标开发板上运行真实的边缘模型，而不是用 Mock 结果冒充推理成功。
3. 将实时预览与低频推理解耦，例如画面持续显示、每 2 至 5 秒对最新帧推理一次。
4. 输出类别、置信度或异常分数、与任务匹配的定位信息、采集时间、模型版本和端到端延迟；目标检测使用检测框，分割使用掩码，分类不强求检测框。
5. 将关键证据图和推理结果可靠上传；断网时暂存，恢复后补传且不产生重复记录。
6. 在前端区分实时画面、对应的推理帧、过期结果、离线状态和模拟数据。
7. 提交数据集报告、训练报告、逐类评测、模型转换一致性报告、相机测试和边缘性能报告。

推荐把第一版范围控制为：一台相机、一块开发板、一至三类设备、一至两类肉眼可见故障、一个边缘节点和一个云端服务。先完成最小真实闭环，再扩充类别、模型和页面。仪表读数 OCR、多摄像头、复杂权限、大模型智能体等都不应挤占模型与相机主链路的时间。

## 二、从我们项目得到的结论

| 应当继承 | 不应照抄 |
| --- | --- |
| 先定义类别、接口和验收，再并行开发 | 先堆页面和接口，最后才发现模型类别无法触发业务规则 |
| 原始数据不可手改，处理后数据可重复生成 | 数据来源只写“来自 GitHub”，不记录链接、许可、版本和哈希 |
| 去重后再按设备、场景或视频分组切分 | 将相邻视频帧或重复图片随机分到训练集和测试集 |
| 报告每个类别的召回率和 AP | 只展示一个总体 mAP，掩盖少数故障类几乎不可用的问题 |
| 候选模型、类别、预处理、阈值和哈希一起版本化 | 文件名仍写旧模型版本，代码、配置和产物互相不一致 |
| 实时流与推理 worker 解耦，推理忙时跳过旧帧 | 每次推理重新打开相机、启动进程和加载模型 |
| Mock 只用于早期接口联调，并在全链路显式标记 | ACL 初始化失败后静默回退 Mock，界面仍显示真实模型在线 |
| PT、ONNX、板端模型使用同一黄金集做一致性测试 | 只证明模型文件存在，不验证转换后数值和精度 |
| 用幂等键、离线队列和 ACK 保证上传 | 证据图上传成功而结果失败后留下孤立数据 |
| 让后端生成事件和告警，前端只展示 | 前端根据临时字符串自行猜测故障状态 |

我们曾将 4 类设备和 21 类状态放进两个模型，总体指标看起来尚可，但部分光伏类别大量漏检；逐类分析后又发现故障召回不足，单纯调低阈值只能带来很小改善，去重并修正数据来源分布后才获得明显提升。这个案例说明：**数据与评测设计通常比盲目换模型、加轮次或调阈值更重要。**

还要明确相机取流方式：

```text
USB UVC 摄像头
     |
开发板/电脑 <- V4L2、OpenCV、FFmpeg
```

老师发的“工业级外观”USB 摄像头，在 Linux 上通常就是一台标准 **UVC** 设备。AI 项目取流用 **UVC + V4L2/OpenCV（或 FFmpeg）** 即可；曝光、增益等优先走标准 UVC 控件。验收重点是连续视频流、断线恢复、预览与低频推理解耦、证据帧对应，以及真实流/本地静图/Mock 可区分。不要把“每次手动上传一张图”说成已经完成实时巡检。

## 三、推荐系统边界

整个系统建议分成五个边界清晰的部分。

| 部分 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| 离线训练环境 | 数据准备、训练、评测、模型导出、实验追踪 | 直接连接现场相机或承担在线业务 |
| 相机适配层 | 枚举设备、配置参数、连续取流、像素格式转换、断线重连 | 训练模型、写数据库或生成业务告警 |
| 边缘推理服务 | 抽帧、预处理、模型推理、后处理、关键帧、缓存与上传 | 保存全系统业务数据或渲染前端 |
| 云端服务 | 设备状态、结果接收、幂等、存储、事件聚合、查询和报告 | 伪造边缘结果或绕过边缘端直接“代替相机采流” |
| 前端 | 实时状态、证据帧、检测框、事件、历史与实验指标 | 根据字符串自行推导告警或掩盖数据过期 |

建议把数据流分成三条：

- **视频数据流**：相机连续取流，边缘端提供预览所需的压缩画面。它要求流畅，但不要求每帧推理或上传。
- **推理证据流**：调度器按周期取“最新完整帧”，经过真实模型生成结果，只上传有意义的证据帧和元数据。
- **控制与状态流**：边缘端上报心跳、相机状态、实际推理引擎和模型版本；云端下发采样周期或模型期望版本。

这三条流不能互相阻塞。前端画面流畅不等于模型在线，模型有结果也不等于结果与当前画面同一帧。

## 四、先想清楚要解决什么

动手前先对齐三件事：

1. **这是不是视觉问题。** 故障能不能在当前镜头、距离、光照下被肉眼稳定看见？人看不清，模型通常也学不好。温度、电流这类不可见量别硬塞进第一版视觉任务；仪表读数是另一条线，不要和故障检测搅在一起。
2. **任务选什么。** 一帧里多个目标且要位置 → 检测；只判断单一主体状态 → 分类；要脏污/裂纹面积 → 分割；几乎只有正常样本 → 再考虑异常检测。第一版多数组做检测即可，但选了分类就不要用检测框那套指标去验收。
3. **类别要窄，错误成本要想清楚。** 宁可先做成「一类设备 + 一两种可见故障」的闭环，也不要一次铺十几种彼此无关的类。想清楚更怕漏检还是更怕误报——后面阈值和评测都按这个取舍。

类别语义也要一致：整台设备框和局部缺陷框不是同一种标法，混着标会把自己绕进去。

## 五、训练前应完成的调研

训练前至少回答以下问题：

1. 目标故障在真实现场有哪些外观形式，是否随设备型号、角度、距离、季节和光照变化？
2. 现有论文、开源项目和商用方案采用检测、分类、分割还是异常检测？
3. 可用数据集的来源、许可证、标注格式、类别语义、分辨率、场景和样本量是什么？
4. 网络数据与老师相机的画面风格差异有多大？是否能采集一批目标相机的域内数据？
5. 开发板的准确型号、SoC、NPU、内存、系统、驱动和推理工具链是什么？
6. 板端支持哪些算子、ONNX opset、输入形状和精度类型？
7. 第一版允许的模型大小、单次推理时延、采样周期和功耗是多少？
8. 最终验收更看重哪一个故障类，最低召回和精度门槛是什么？

调研结论应形成一页决策记录，至少比较两个候选模型、两个数据方案和单模型/级联两种架构，并说明选择理由。不要以“YOLO 比较常用”作为唯一理由。

还可以在 Kaggle、Roboflow Universe、Figshare、Dataset Ninja、GitHub、Gitee、百度 AI Studio、天池和相关论文附件中检索。搜索时组合设备名称、故障名称、`dataset`、`object detection`、`YOLO`、`COCO`、`VOC` 等关键词。

网络数据不能取代自己采集的数据。至少应使用老师提供的相机采集正常、安全替代物、不同距离、不同角度、明暗变化、模糊和空场景图片。采集完成后先按设备、拍摄批次或视频分组，再划分用于调阈值的域内验证集和只使用一次的现场测试集；同一连拍或相邻视频帧不得跨集。

任何数据集进入项目之前，都要建立来源记录：稳定链接、提供者、许可证、下载日期、归档文件 SHA-256、原始类别、标注格式、允许用途、引用方式和本项目采用/排除的类别。只写“来源于 GitHub”视为来源不合格。

## 七、训练

核心思想：**先做小而可信的基线，再单变量改进；类别少、能上板，比堆复杂结构重要。**

- 冒烟跑通 → 完整基线 → 看错例 → 再改数据或模型，不要一次改五个旋钮。
- 边缘优先小模型；准确率和时延、内存要实测权衡。
- 第一版优先单模型。所谓级联必须真的做 ROI 裁剪和坐标还原，整图双模型并行不要自称级联。
- 交给边缘的不只是权重文件，还要带着类别顺序、预处理/后处理约定和几张对照用的正负样例。

## 八、评测

核心思想：**总体 mAP 好看不等于能用；要按类看，并在目标相机域上验证。**

- 检测至少看逐类 Precision / Recall / AP，以及典型漏检误检；不要只报一个总数掩盖弱类。
- 阈值只在验证集上选，冻结后再测测试集。
- 网络测试集分数高，仍要做老师相机（或本场景）上的评测。
- 安全替代物只能证明链路通，不能夸大成真实故障召回。禁止自行制造危险故障。

## 九、相机接入

课上常见是 USB **UVC** 摄像头（外壳常叫工业相机）。板端日常路径：

**UVC + V4L2 / OpenCV / FFmpeg（常见 `/dev/video0`），参数走标准 UVC 控件。**

正确结构是：**采集线程持续写入最新帧；预览读压缩副本；推理按周期抽最新完整帧；上传异步发证据。** 上一帧还在推理就应跳过，不要排过期长队。

先做到能枚举设备、连续取流、断线重连，再接模型。**禁止用「每次手动抓一张再上传」代替连续视频流。** 结果必须和对应证据帧对齐，不能把旧框画在新画面上假装实时。

## 十、板端部署

按依赖递增推进：训练框架正确 → ONNX 对齐 → 板端模型对齐 → 再接相机。转换成功只说明图能编译，还要用同一批样例对照类别、框/分数是否一致。服务常驻加载模型，失败要显式报错，**禁止静默回退 Mock 却显示真实在线**。

## 十一、边云与前端

- **边缘**：抽帧、推理、本地暂存、上传；断网可补传且避免重复记录。
- **云端**：收结果、做幂等、聚合事件与告警、提供查询；别让前端靠猜字符串判故障。
- **前端建议四个面**：系统状态、实时巡检（连续流 + 对应证据帧）、故障中心、历史/指标。真实流、Mock、过期、离线必须分得清。

大模型建议若要用，只能解释和整理，不能改写原始检测证据。

## 十二、联调顺序

逐段加真实依赖，哪一步坏就查哪一步：

1. 固定图片在训练框架正确
2. 同图在 ONNX 对齐
3. 同图在开发板对齐
4. 板上 UVC 稳定取流
5. 取流与模型接上且预览/推理互不阻塞
6. 结果上传云端并幂等保存
7. 前端吃真实接口

Mock 可以提前联调后端和页面，最终必须用真实相机和真实板端模型再跑通，并标明数据来源。

## 十三、怎样算靠谱

- 相机要连续跑得住，不是偶发拍一张。
- 模型要在本域数据上按类说得清，弱类不能藏。
- 转换后结果要和训练侧对得上。
- 上传、断网恢复、前端状态要说得清。
- 硬红线：未标明的 Mock 冒充真实；只有本地图/手动单张、没有连续流实测；只有电脑推理没有板端实测；训测泄漏；证据帧对不上却说实时识别；密钥进仓库。

## 十四、再往后

闭环稳了再谈：本域难例回流、量化与流水线加速、跟踪减重复告警、更强存储与可观测性、扩类别。顺序永远是：**先补证据最薄的一环，再加功能。** 一个解释得清楚、链路真实的窄系统，好过页面很多却靠 Mock 的大平台。

## 结语

这份说明只给问题拆解和工程方向，不替你做实现选择。把 AI 当助手可以，但数据、模型、相机、板端和云端之间的边界，需要亲手验证清楚。
