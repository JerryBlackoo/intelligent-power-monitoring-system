# 基于边缘设备与工业相机的智能电力巡检系统

> 人工智能电力系统应用实训指导

## 关于本仓库

本仓库有意删除了过去项目中的全部源代码、模型权重、数据集、数据库、运行产物、账号配置与旧 Git 历史，只保留这一份实验指导。它不是一个可以直接运行的项目模板，也不提供可以原样提交的课程答案。

生成式人工智能已经显著降低了编写代码的成本，但它不能替代任务定义、数据治理、实验设计、接口契约、硬件调试、性能测量和结果解释。后续同学应从本指南出发建立自己的仓库和实现，并能够说明每个选择为什么合理、每项指标如何得到、每个演示结果是否来自真实相机和真实边缘模型。

本指南来自对两个往届原型的完整复盘。保留下来的是可迁移的方法，舍弃的是与个人电脑路径、临时网络地址、演示数据和特定代码结构绑定的实现。

## 一、课程目标

本课程的目标不是做一个界面看起来完整的监控大屏，而是完成一条有证据、可复现、可测量的真实链路：

**工业相机持续采集画面，边缘设备按设定周期选取最新帧并运行真实模型，云端保存证据和结构化结果，前端同步展示设备状态、识别结果、历史事件与性能数据。**

最终系统至少应做到：

1. 使用老师提供的工业级摄像头持续获得稳定画面，而不是只读取演示图片。
2. 在目标开发板上运行真实的边缘模型，而不是用 Mock 结果冒充推理成功。
3. 将实时预览与低频推理解耦，例如画面持续显示、每 2 至 5 秒对最新帧推理一次。
4. 输出类别、置信度或异常分数、与任务匹配的定位信息、采集时间、模型版本和端到端延迟；目标检测使用检测框，分割使用掩码，分类不强求检测框。
5. 将关键证据图和推理结果可靠上传；断网时暂存，恢复后补传且不产生重复记录。
6. 在前端区分实时画面、对应的推理帧、过期结果、离线状态和模拟数据。
7. 提交数据集报告、训练报告、逐类评测、模型转换一致性报告、相机测试和边缘性能报告。

推荐把第一版范围控制为：一台相机、一块开发板、一至三类设备、一至两类肉眼可见故障、一个边缘节点和一个云端服务。先完成最小真实闭环，再扩充类别、模型和页面。仪表读数 OCR、多摄像头、复杂权限、大模型智能体等都不应挤占模型与相机主链路的时间。

## 二、从往届项目得到的结论

| 应当继承 | 不应照抄 |
| --- | --- |
| 先定义类别、接口和验收，再并行开发 | 先堆页面和接口，最后才发现模型类别无法触发业务规则 |
| 原始数据不可手改，处理后数据可重复生成 | 数据来源只写“来自 GitHub”，不记录链接、许可、版本和哈希 |
| 去重后再按设备、场景或视频分组切分 | 将相邻视频帧或重复图片随机分到训练集和测试集 |
| 报告每个类别的召回率和 AP | 只展示一个总体 mAP，掩盖少数故障类几乎不可用的问题 |
| 候选模型、类别、预处理、阈值和哈希一起版本化 | 文件名仍写旧模型版本，代码、配置和产物互相不一致 |
| 实时流与推理 worker 解耦，推理忙时跳过旧帧 | 每次推理重新打开相机、启动进程和加载模型 |
| Mock 只用于早期接口联调，并在全链路显式标记 | ACL 初始化失败后静默回退 Mock，界面仍显示真实模型在线 |
| PT、ONNX、板端模型使用同一黄金集做一致性测试 | 只证明模型文件存在，不验证转换后数值和精度 |
| 用幂等键、离线队列和 ACK 保证上传 | 证据图上传成功而结果失败后留下孤立数据 |
| 让后端生成事件和告警，前端只展示 | 前端根据临时字符串自行猜测故障状态 |

往届项目曾将 4 类设备和 21 类状态放进两个模型，总体指标看起来尚可，但部分光伏类别大量漏检；另一项目在逐类分析后发现故障召回不足，单纯调低阈值只能带来很小改善，去重并修正数据来源分布后才获得明显提升。这个案例说明：**数据与评测设计通常比盲目换模型、加轮次或调阈值更重要。**

还要明确一个硬件边界：往届两个项目实测的都是普通 UVC 摄像头和 `/dev/video0`，不是工业相机厂商 SDK 的完整接入。工业相机部分必须从设备识别和厂商资料重新开始，不能把 OpenCV 能打开普通摄像头当作验收完成。

## 三、推荐系统边界

整个系统建议分成五个边界清晰的部分。

| 部分 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| 离线训练环境 | 数据准备、训练、评测、模型导出、实验追踪 | 直接连接现场相机或承担在线业务 |
| 相机适配层 | 枚举设备、配置参数、连续取流、像素格式转换、断线重连 | 训练模型、写数据库或生成业务告警 |
| 边缘推理服务 | 抽帧、预处理、模型推理、后处理、关键帧、缓存与上传 | 保存全系统业务数据或渲染前端 |
| 云端服务 | 设备状态、结果接收、幂等、存储、事件聚合、查询和报告 | 伪造边缘结果或控制相机底层 SDK |
| 前端 | 实时状态、证据帧、检测框、事件、历史与实验指标 | 根据字符串自行推导告警或掩盖数据过期 |

建议把数据流分成三条：

- **视频数据流**：相机连续取流，边缘端提供预览所需的压缩画面。它要求流畅，但不要求每帧推理或上传。
- **推理证据流**：调度器按周期取“最新完整帧”，经过真实模型生成结果，只上传有意义的证据帧和元数据。
- **控制与状态流**：边缘端上报心跳、相机状态、实际推理引擎和模型版本；云端下发采样周期或模型期望版本。

这三条流不能互相阻塞。前端画面流畅不等于模型在线，模型有结果也不等于结果与当前画面同一帧。

## 四、第一阶段：先定义问题

### 4.1 判断问题是否适合视觉方案

开题前先回答：故障是否能从当前镜头、距离、光照和分辨率下被肉眼稳定看见？如果人看不清，模型通常也学不好。温度、电流、绝缘性能等不可见状态应由传感器解决；仪表读数属于检测、透视校正和 OCR 的独立任务，不要混入第一版故障检测。

### 4.2 选择合适任务

| 任务 | 适用情况 | 主要指标 |
| --- | --- | --- |
| 目标检测 | 一帧有多个目标，需要类别和位置 | 逐类 Precision、Recall、AP、漏检与误检 |
| 图像分类 | 画面或裁剪区域只有一个主体，只判断状态 | Macro-F1、Balanced Accuracy、召回率 |
| 实例/语义分割 | 污渍、裂纹、烟雾等形状不规则，需要面积 | mIoU、Dice、边界误差 |
| 异常检测 | 缺陷样本极少、正常样本多，且能接受后续人工复核 | AUROC、AUPRC、异常召回、每图误报 |

课程第一版通常优先目标检测，本文后续的检测框、IoU 和 NMS 条款默认针对这条主线。若设备框固定且只判断开关状态，分类可能比再训练一个大检测器更合理；若要测光伏板污渍面积，分割比把污渍框强行映射成“光伏板”更合理。

选择分类、分割或异常检测时，必须在开题阶段经教师确认，并用对应条款替换检测专属条款，不能一边选择分类、一边用检测框指标验收：

| 任务 | 边缘输出 | 黄金集主要比较 | 前端主要展示 |
| --- | --- | --- | --- |
| 目标检测 | 类别、置信度、原图坐标框 | 类别、框、置信度、NMS 后结果 | 对应证据帧和检测框 |
| 图像分类 | 类别、概率、输入 ROI 标识 | Top-1 类别、各类概率或容差 | 对应证据帧、ROI 和状态 |
| 分割 | 类别、分数、掩码或受控掩码 URI | 类别、掩码 IoU/Dice 和面积 | 对应证据帧和半透明掩码 |
| 异常检测 | 异常分数、阈值版本、可选热力图 | 分数容差、阈值判定和热力图 | 对应证据帧、分数和热力图 |

### 4.3 冻结类别语义

在下载数据之前先写“类别定义表”，每一类至少包含中文名、英文标识、正例、反例、易混淆类、标注对象和业务含义。

尤其注意：整台设备框和局部缺陷框不是同一种标注语义。一个损坏绝缘子的整件框与其破损区域框不能未经设计就映射成互斥的“正常绝缘子”和“损坏绝缘子”。可以选择统一标整件设备状态，也可以用设备检测加局部缺陷检测，但必须保持所有数据源的规则一致。

建议第一版围绕一个核心对象形成完整闭环，例如“绝缘子正常/表面损伤”，而不是一次收集大量彼此无关的设备和故障类别。

### 4.4 定义错误成本

电力巡检通常更怕漏掉真实故障，因此核心故障类应优先保证 Recall，同时设置 Precision 下限避免告警泛滥。开题时就写明：漏检一次和误报一次分别造成什么后果，最终阈值将如何选择。

### 4.5 冻结验收基线

正式采集和训练前，由小组与教师共同填写并签字确认《验收基线表》。基线表把条款分为四级：一票否决、必须达到、目标值和仅报告项。后续章节给出的数值是没有另行约定时的默认协议；教师可以在开题时调整，但不能在看过测试集结果后改门槛。

基线表至少冻结：

| 项目 | 必须写清的判定口径 |
| --- | --- |
| 任务与输出 | 检测、分类、分割或异常检测；输出字段、坐标/掩码/分数语义和版本 |
| 核心类与错误成本 | 哪些类是核心故障；漏检和误报的优先级；哪些数值为必达或目标 |
| 数据与分组 | 数据版本；按设备、场站、拍摄批次或视频的分组键；训练/验证/测试清单 |
| 最小测试规模 | 默认检测主线每个核心类不少于 50 个真实实例且来自至少 3 个独立组；不足时只作探索性结论 |
| 指标端点 | 检测默认以 IoU 0.50 匹配，置信度在验证集选择后冻结；其他任务填写对应判定规则 |
| 性能协议 | 硬件、分辨率、像素格式、模型版本、采样周期、预热次数和计时范围 |
| 重复次数 | 默认预热 10 次后测量至少 200 个推理周期；相机稳定运行至少 30 分钟 |
| 网络协议 | 默认稳定网络至少 300 次上传；断网 10 分钟；恢复后的补传时限、缓存容量和溢出策略 |
| 时延端点 | 分别定义采集到推理完成、采集到云端 ACK、采集到前端展示，不混成一个“端到端” |
| 安全边界 | 可使用的真实故障数据、教师批准试验台和安全替代物；明确禁止的造障行为 |

本阶段交付物是《任务定义与类别规范》和《验收基线表》，未经指导教师确认，不进入正式标注和训练。

## 五、训练前应完成的调研

训练前至少回答以下问题：

1. 目标故障在真实现场有哪些外观形式，是否随设备型号、角度、距离、季节和光照变化？
2. 现有论文、开源项目和商用方案采用检测、分类、分割还是异常检测？
3. 可用数据集的来源、许可证、标注格式、类别语义、分辨率、场景和样本量是什么？
4. 网络数据与老师相机的画面风格差异有多大？是否能采集一批目标相机的域内数据？
5. 开发板的准确型号、SoC、NPU、内存、系统、驱动和推理工具链是什么？
6. 板端支持哪些算子、ONNX opset、输入形状和精度类型？
7. 第一版允许的模型大小、单次推理时延、采样周期和功耗是多少？
8. 最终验收更看重哪一个故障类，最低召回和精度门槛是什么？

调研结论应形成一页决策记录，至少比较两个候选模型、两个数据方案和单模型/级联两种架构，并说明选择理由。不要以“YOLO 比较常用”作为唯一理由。

下面是往届项目实际调研过的入口，只作为搜索起点，不代表可以不经审查直接合并。

| 方向 | 入口 | 注意事项 |
| --- | --- | --- |
| 变电站设备 15 类 | <https://figshare.com/articles/dataset/A_YOLO_Annotated_15-class_Ground_Truth_Dataset_for_Substation_Equipment/24060960> | 类别较多，只选语义明确且与任务一致的类 |
| 航拍电力设施与绝缘子缺陷 | <https://github.com/supervisely-ecosystem/aerial-power-infrastructure-detection-train-dataset> | Supervisely 标注；航拍域未必等于地面工业相机域 |
| 绝缘子缺陷 | <https://datasetninja.com/insulator-defect-detection> | 记录原始类别、许可和下载版本 |

| 变压器站检测 | <https://universe.roboflow.com/mehran-uet-jamshtoro/transformer-station-detection> | 样本较少，先检查 damage/normal 的标注范围 |
| 火焰与烟雾候选 | <https://github.com/gaia-solutions-on-demand/DFireDataset> | 仓库可能只有说明，完整数据在外部平台 |
| 火焰烟雾补充集 | <https://github.com/siyuanwu/DFS-FIRE-SMOKE-Dataset> | 检查下载入口、许可和现场域差异 |

还可以在 Kaggle、Roboflow Universe、Figshare、Dataset Ninja、GitHub、Gitee、百度 AI Studio、天池和相关论文附件中检索。搜索时组合设备名称、故障名称、`dataset`、`object detection`、`YOLO`、`COCO`、`VOC` 等关键词。

网络数据不能取代自己采集的数据。至少应使用老师提供的相机采集正常、安全替代物、不同距离、不同角度、明暗变化、模糊和空场景图片。采集完成后先按设备、拍摄批次或视频分组，再划分用于调阈值的域内验证集和只使用一次的现场测试集；同一连拍或相邻视频帧不得跨集。

任何数据集进入项目之前，都要建立来源记录：稳定链接、提供者、许可证、下载日期、归档文件 SHA-256、原始类别、标注格式、允许用途、引用方式和本项目采用/排除的类别。只写“来源于 GitHub”视为来源不合格。

## 七、数据集应怎样处理

### 7.1 建立数据分层

逻辑上至少区分：下载归档、只读原始数据、人工审查区、可重复生成的处理后数据、清单与报告。原始数据不得直接改名、重标或删除；格式转换、类别映射和切分必须能够从原始数据重新执行。

数据集本体通常不提交普通 Git。可以使用受控共享存储、对象存储或数据版本工具；仓库中保留清单、哈希、来源说明、标注规范和生成方法。模型大文件同样应通过制品存储或 Git LFS 管理。

### 7.2 先去重，再切分

相同图片、压缩版本、相邻视频帧和同一设备连拍必须归为同一组。建议结合文件哈希、感知哈希和人工复核去重，然后按 `site_id`、`device_id`、`video_id` 或来源组切分，禁止简单按图片随机切分造成泄漏。

训练、验证、测试集的职责不同：

- 训练集用于学习，可以增强、重采样和类别平衡。
- 验证集用于选模型和调阈值，不得重采样。
- 测试集只在方案冻结后做最终一次评测，不参与调参。
- 目标相机数据也要分为域内验证集和独立现场测试集，按设备、批次或视频分组；两者分别报告样本量，不能用同一批帧既调参又作为现场结论。

### 7.3 保留负样本和困难样本

没有目标的空画面、相似设备、反光、阴影、污点、人物和背景都是重要负样本。检测任务的格式转换不能因为“映射后没有框”就丢弃所有负样本；其他任务也要保留符合其定义的正常/背景样本。否则模型在干净验证集上很好看，到真实现场却会频繁误报。

### 7.4 审查类别与来源偏差

统计每个 split 的图片数、标注数、每类实例数和来源占比；检测任务再统计目标框、空标注和目标尺寸，分割任务统计掩码面积，分类/异常检测统计标签与正常/异常比例。尤其检查“某一来源几乎全是故障，另一来源几乎全是正常”的情况；模型可能学会背景和拍摄风格，而不是故障本身。

重采样只能作用于训练集。少数类可以采用补采、复核标注、合理重复、采样权重或困难样本挖掘，但不能复制验证/测试样本来美化指标。

### 7.5 数据准入门槛

正式训练前至少完成：

- 类别文件、数据配置和标注 ID 顺序一致。
- 任务标注合法：检测框无负宽高或越界，分割掩码尺寸正确，分类/异常标签符合冻结语义。
- 图片与标签一一对应，空标注有明确含义。
- 随机抽查和按类抽查均通过可视化检查。
- 重复组不跨 split。
- 每个核心类在验证和测试中都有足够实例；样本不足时明确标为弱类。
- 保存数据版本、来源分布、排除规则和统计报告。

## 八、模型应怎样训练

### 8.1 先建立小而可信的基线

推荐流程是：环境检查、数据校验、极小数据转换、1 个 epoch 冒烟训练、完整基线训练、独立验证、错误样例分析、单变量改进。不要一开始同时修改模型、输入尺寸、增强、优化器和数据比例，否则无法解释提升来自哪里。

边缘场景优先从成熟的小模型开始。模型越大、输入分辨率越高，细小目标可能更容易识别，但训练和板端推理成本也会增加。应在准确率、端到端时延、内存、温升和采样周期之间做实测权衡，并确认所用框架和权重许可证满足课程及后续用途。

### 8.2 检测主线的单模型、并行双模型与真正级联

| 方案 | 特点 | 适用条件 |
| --- | --- | --- |
| 单模型 | 实现最简单，延迟低，类别契约统一 | 第一版和类别较少时优先 |
| 两模型整图并行 | 两个模型都看整图，结果需要去重和关联 | 仅用于对照实验，不应称为级联 |
| 设备检测后 ROI 级联 | 先定位设备，再对裁剪区域做状态判断 | 小缺陷需要放大，且能接受误差累积和额外延迟 |

级联必须真的完成 ROI 裁剪、坐标还原、设备与缺陷关联和无设备框时的策略。级联整体召回受每一级限制，不能只报告两个模型各自的离线指标。

分类、分割或异常检测方案也应先完成一个可部署的单模型基线；只有当设备定位确实能改善下游任务时，再引入检测加分类/分割等组合，并评估前级漏检造成的整体损失。

### 8.3 保存完整实验身份

每次实验至少记录：实验编号、数据版本、切分清单、代码提交、环境锁文件、框架版本、基础权重、随机种子、输入尺寸、batch、epoch、优化器、学习率、增强、早停、最佳轮次、运行设备和训练时长。

脚本中的配置必须与产物中的实际参数一致。路径应来自参数或配置，不得写死个人电脑盘符和用户名。

### 8.4 模型交付包

训练成员交给边缘成员的不是一个孤立权重文件，而是一套不可拆分的模型包：

- 训练权重和可交换模型。
- 精确类别顺序与业务映射。
- 输入节点名、形状、dtype、颜色顺序、缩放/letterbox、归一化和 layout。
- 与任务匹配的后处理方式；检测任务记录置信度、NMS 阈值及是否按类别 NMS，分类/分割/异常检测记录各自阈值和输出解释。
- 数据版本、模型版本、框架版本和所有文件哈希。
- 至少一组正例、负例和边界样例的黄金输入与期望输出。
- 独立评测报告和已知失败模式。

候选模型只有经过评测、转换和板端验证后才能“晋升”为部署模型，不能因为文件已经生成就覆盖稳定版本。

## 九、模型应怎样评测

### 9.1 不只看总体 mAP

目标检测至少报告：

- 每类真实实例数、Precision、Recall、F1、AP@0.5 和 AP@0.5:0.95。
- 总体指标和宏平均，不能只给按大类加权后的结果。
- 混淆矩阵、PR 曲线、F1-阈值曲线、典型误检和漏检图。
- 小/中/大目标、不同光照、距离、角度、模糊和遮挡分片结果。
- 空场景每图误报数或连续视频每分钟误报数。

分类应报告 Macro-F1、Balanced Accuracy、混淆矩阵和核心故障召回；分割应报告逐类 mIoU、Dice 和失败样例。电力故障场景还应报告事件级漏报率与首次检出延迟。

### 9.2 阈值只能在验证集上选择

根据验证集扫描工作阈值并按错误成本选工作点。检测任务绘制 Precision/Recall/F1 变化；分类、分割和异常检测采用各自的概率、面积或异常分数阈值。阈值冻结后再评测测试集，不能看过测试结果后继续调阈值。

### 9.3 必须有目标相机现场评测

网络数据集上的高指标不代表目标相机可用。独立现场测试集应包含正常运行、经批准的真实故障数据或安全替代物、空场景、相似物体、曝光变化、运动模糊、遮挡和重新插拔相机后的画面。该现场测试集不能参与阈值选择或候选模型晋升。

安全替代物只能证明采集、推理、上传和展示链路工作，不能证明真实故障识别能力，也不能计入真实故障 Recall。禁止学生自行制造带电设备故障、短路、明火、烟雾、设备破坏或其他危险场景；真实故障评测只能使用来源获批的数据、教师监督的安全试验台或已有合法记录。

### 9.4 默认目标与判定口径

不同题目由《验收基线表》决定哪些数字是必达、目标或仅报告。若没有另行约定，目标检测主线采用以下默认目标，它们不是生产安全承诺：

- 核心故障类至少有 50 个真实实例、来自至少 3 个独立组；在冻结置信度阈值和 IoU 0.50 匹配规则下，Recall 目标不低于 0.80，Precision 目标不低于 0.70。
- 每个必做类都必须单独报告；任何类 AP@0.5 低于 0.60 都应说明原因和改进计划。
- 分别报告网络测试集与独立现场测试集；下降幅度以相同指标的绝对差给出，超过基线表约定值时进行域偏差分析。
- 漏检样例必须分类归因到数据、标注、分辨率、阈值、预处理或场景问题。

若某数字在基线表中被列为“必须达到”，未达到即不能通过该项；若列为“目标值”，未达到可以形成有证据的实验结论，但必须完成归因和改进实验。隐瞒弱类、只给总体数字或用训练集截图代替独立评测不予验收。

## 十、工业相机应怎样接入

### 10.1 先完成硬件清单

拿到设备后第一天填写并保存以下信息：

| 项目 | 需要确认的内容 |
| --- | --- |
| 开发板 | 商业型号、SoC/NPU、系统、内核、CPU 架构、内存、驱动和推理工具链版本 |
| 相机 | 厂商、型号、序列号、传感器、接口、供电方式和固件 |
| 镜头 | 接口、焦距、光圈、工作距离、视场和目标最小像素尺寸 |
| SDK | 名称、版本、下载来源、是否支持 Linux/aarch64、语言绑定和示例程序 |
| 采集 | 分辨率、帧率、像素格式、bit depth、触发模式、曝光、增益和白平衡 |
| 网络/总线 | GigE 的 IP/子网/包大小，USB3 的带宽/供电/权限，MIPI 的 media pipeline |

不要先假设工业相机一定会出现在 `/dev/video0`。不同接口应选择不同路径：

- UVC 摄像头可以使用 V4L2、FFmpeg、GStreamer 或 OpenCV。
- USB3 Vision 和 GigE Vision 通常优先使用厂商 SDK 或兼容的 GenICam 实现。
- GigE 相机还需处理固定 IP、同网段、网卡缓冲、包大小、丢包和可能的 PTP 时间同步。
- MIPI CSI 相机需确认设备树、传感器驱动、media graph 和 ISP。
- 网络相机若只提供 RTSP，则使用适合的流媒体解码链路。

### 10.2 按阶段验收，不要直接接模型

1. **枚举**：系统和官方 SDK 能找到相机，记录型号、序列号和接口状态。
2. **单帧**：官方样例能保存一张原始图，颜色、尺寸和曝光正确。
3. **连续流**：保持同一相机会话连续采集，帧号和时间戳单调，统计实际 FPS 和丢帧。
4. **参数控制**：验证曝光、增益、白平衡、像素格式、ROI 和触发模式的读写结果。
5. **像素转换**：明确 Bayer、Mono、YUV、RGB/BGR、stride 和 bit depth，验证转换后的颜色和几何尺寸。
6. **稳定性**：连续运行至少 30 分钟，测试拔插、超时、断线和恢复，不靠人工重启。
7. **目标成像**：在真实工作距离下检查对焦、运动模糊、过曝、欠曝和目标像素尺寸。

只有以上门槛通过后，才把相机接入推理服务。厂商 SDK 回调中只做必要复制和入队，不要执行模型、网络请求或磁盘写入。

### 10.3 正确的实时与抽帧结构

边缘端应维持一个长期存在的相机句柄和一个有上限的最新帧缓冲区：

**相机采集线程持续写入最新帧；预览线程读取压缩副本；推理调度器每隔若干秒取最新完整帧；上传线程发送证据与结果。**

初始推理周期可设为 3 秒，再根据模型 p95 本地关键路径时延和场景变化速度调整。若上一帧仍在推理，下一次调度应跳过并记录 `skipped_busy`，而不是排成长队处理过期画面。

时间记录至少包括相机硬件帧号与硬件时间戳（SDK 提供时）、主机收到帧时的 UTC 时间和用于计算时延的单调时钟。硬件时间戳对应曝光/采集时刻，主机时间反映 SDK 缓冲后的到达时刻，二者不能混用或在上传时补写。多设备比较前记录 NTP/PTP 同步方式和测得的时钟偏差。

实时预览可按场景选择 MJPEG、HLS 或 WebRTC。MJPEG 实现简单，适合局域网课程演示；HLS 延迟较高；WebRTC 低延迟但复杂。展示结果必须对应同一证据帧：检测叠加框、分割叠加掩码、分类/异常检测显示该帧的状态，不能把五秒前的结果标成当前视频结果。

### 10.4 相机状态机

相机服务至少区分：初始化、运行、降级、重连、离线和停止。读取失败后释放句柄并按退避策略重连；健康接口展示实际状态、最近帧时间、累计帧、丢帧、重连次数、像素格式和错误原因。

工业现场还要遵守用电安全、设备固定和隐私要求。该系统只能作为教学巡检辅助，不能被描述为保护、跳闸或安全联锁系统。

## 十一、模型如何部署到边缘设备

### 11.1 先确认目标环境

开发板型号相近不代表编译目标相同。必须从目标板重新确认 SoC、NPU、驱动、CANN/ACL、ATC、Python/C++ 运行时和相机 SDK 架构。往届曾使用 Atlas 200I A2、Ascend310B4 和对应 CANN 环境，但新设备不得直接照抄该参数。

### 11.2 分级通过转换门禁

建议按以下顺序：训练权重本地推理、导出 ONNX、ONNX 结构检查、ONNX Runtime 单图对齐、面向准确 SoC 转换板端模型、板端零输入冒烟、板端黄金图片推理、最后接相机。

每次导出和转换都保存工具版本、完整参数、输入输出节点、静态/动态形状、精度类型、日志和文件 SHA-256。转换成功只说明图能编译，不能说明预处理、后处理和精度正确。

### 11.3 使用黄金集验证一致性

选择至少 10 张包含正例、负例和边界情况的固定图片，保存训练框架输出作为参考。检测任务还应包含小目标和多目标，并比较类别、数量、坐标、置信度和 NMS 后结果；分类比较类别与概率；分割比较掩码；异常检测比较分数、判定和可选热力图。

浮点实现可能有小差异，应按任务提前约定容差。检测任务可从框坐标 4 像素、置信度绝对差 0.05 起步；其他任务冻结概率、掩码 IoU 或异常分数容差。超出容差时排查颜色顺序、缩放/letterbox、归一化、layout、输出解析和任务后处理。最终还应在完整测试集上比较精度漂移，而不只比较几张图。

### 11.4 边缘运行时要求

- 服务启动时初始化 NPU、创建 context、加载模型并分配缓冲；每帧复用，退出时完整释放。
- 预处理、模型执行、后处理和可视化分别计时；另行报告采集到推理完成、采集到云端 ACK、采集到前端展示三条时延的 p50/p95。
- `camera_fps`、`inference_fps` 和 `sampling_interval` 是三个不同指标，不能混写。
- 模型实际加载版本、类别版本、配置版本和引擎类型写入每条结果。
- 真实验收模式下模型初始化失败必须明确失败，禁止自动回退 Mock。
- 模型更新先下载到暂存区，验证哈希与黄金样例后原子切换；失败时回滚。
- 使用服务管理器实现开机启动、崩溃重启、日志轮转和优雅停止，不使用模糊的强制杀进程命令。

## 十二、边缘端和云端服务怎样搭建

### 12.1 边缘端服务

边缘服务建议包含相机适配器、最新帧缓冲、推理调度器、模型运行时、事件/关键帧选择器、本地 outbox、上传客户端和健康监控。各部分用清晰接口连接，使相机、模型和云端可以分别用测试替身联调。

每条上传记录至少携带：节点、相机、巡检、帧号、硬件/主机采集时间、图像尺寸、真实/模拟来源、模型与类别版本、任务类型、结构化结果、证据图标识，以及预处理、推理、后处理和约定的时延。检测任务统一使用原图像素框并在云端校验；分割任务约定掩码尺寸与编码；分类和异常检测保留输入 ROI 或整帧标识。

边缘端先把待上传记录落入有上限的 outbox，再异步上传；成功收到 ACK 后确认。网络中断、超时、限流和 5xx 属于可重试错误，在保留期限内持续退避，离线期间不因重试计数耗尽而丢弃；确定无法修复的 4xx 或数据校验错误进入可审计、可人工重放的 dead-letter。每帧使用稳定幂等键，重复发送只得到同一业务结果。

默认断网测试为 10 分钟，outbox 至少容纳该时长预计记录数的 2 倍；若基线表未另行规定，网络恢复后 5 分钟内完成补传且不产生重复记录。容量满时优先保留故障首次出现、变化和恢复帧，可丢弃最旧的正常周期帧，但必须累计并上报丢弃数，任何记录都不得静默消失。

### 12.2 关键帧与事件

第一版可以固定周期采样，但应逐步加入事件策略：正常状态低频记录；首次出现故障立即记录；持续故障按较低频率更新；故障恢复记录一次；目标类别和框位置长期不变时减少重复上传。

事件去抖不能只看单帧。可要求连续若干次命中才打开事件，连续若干次未命中才关闭事件，并保留最高置信度或最清晰证据。具体窗口应通过验证视频实验确定。

### 12.3 云端服务

课程项目使用单体后端足够，不必一开始拆微服务。后端至少负责：

- 节点注册、鉴权、心跳和实际在线状态计算。
- 巡检生命周期、证据上传和结构化结果接收。
- 幂等保存、任务输出、坐标/掩码/分数和枚举校验。
- 设备、结果、事件、告警、处理状态和报告查询。
- 模型与配置的期望版本记录，以及边缘更新 ACK。
- 图片保留策略、日志、审计和错误响应。

元数据适合放关系数据库，原始图和标注图放文件/对象存储，数据库保存受控 URI 和哈希。开发阶段可用 SQLite，涉及并发、多用户或长期运行时优先使用 PostgreSQL 等服务型数据库并建立迁移。

边缘 API 使用独立设备凭据、TLS、请求大小限制和超时；密码必须使用成熟哈希算法，权限必须由后端验证，密钥不得进入前端或 Git。上传图片要校验大小、类型和实际文件内容，所有展示文本要安全转义。

大模型维修建议属于可选增强。告警应由确定性规则和视觉结果产生，大模型只负责解释、整理和生成供人工复核的建议；调用失败时显示明确降级状态，不能改变原始检测证据。

## 十三、前端应该展示什么

推荐只做四个工作视图：

1. **系统总览**：边缘节点、工业相机、实际模型、云端连接、最后心跳和资源状态。
2. **实时巡检**：连续画面、与结果对应的证据帧、任务输出、类别、分数、采集时间和分阶段时延；检测显示框，分割显示掩码，分类/异常检测显示状态。
3. **故障中心**：聚合事件、风险、首次/最后出现时间、最佳证据、处理状态和人工备注。
4. **报告与实验**：历史巡检、模型版本、逐类指标、边缘性能和导出报告。

前端必须清楚呈现以下状态：正在连接、无帧、相机离线、模型未加载、推理失败、后端离线、结果过期、Mock、录制视频回放和真实相机。旧结果可以保留，但必须标注“最近一次结果”和时间，不能伪装为当前识别。

检测任务的框应按原图尺寸和页面实际显示区域做坐标缩放，并处理 letterbox 留白；分割掩码同样需要正确缩放。实时流与推理帧无法严格同步时，优先展示对应证据图及其结果，而不是在当前视频上叠加旧结果。

## 十四、正确的联调顺序

按以下顺序逐段增加真实依赖，每一步失败时只排查当前边界：

1. 固定本地图片在训练框架中得到正确结果。
2. 同一图片在 ONNX 中对齐。
3. 同一图片在开发板模型中对齐。
4. 厂商样例稳定读取工业相机。
5. 自己的相机适配层稳定取流，不接模型。
6. 从相机保存的一帧在边缘模型中正确推理。
7. 实时预览和周期推理同时运行且互不阻塞。
8. 边缘结果写入本地 outbox，并上传到云端测试接口。
9. 云端完成幂等保存、事件生成和查询。
10. 前端消费真实接口，最后再加入报告和可选智能建议。

Mock 可以帮助第 8 至 10 步提前并行开发，但最终必须用真实相机与真实板端模型重复整个链路，并在界面和记录中保留数据来源。

## 十五、测试与量化验收

### 15.1 必须覆盖的故障注入

系统测试至少主动制造：相机启动失败、相机中途断开、坏帧、曝光异常、模型文件缺失、模型输出形状错误、NPU 初始化失败、推理超时、网络断开、云端超时或 500、重复上传、磁盘空间不足、进程重启和时钟偏差。

每一种故障都应有预期状态、日志、恢复策略和数据一致性检查。失败不能被解释成“画面中没有目标”。

故障注入只针对软件、网络和可安全断开的教学硬件。禁止为测试人为制造带电故障、短路、明火、烟雾或破坏相机/电力设备；相关视觉输入使用获批数据、录制材料或教师监督的安全试验台。

### 15.2 默认验收协议

以下是未被《验收基线表》替换时的默认协议。所有比率都同时报告分子、分母和排除原因。

| 维度 | 默认判定 |
| --- | --- |
| 相机 | 目标分辨率和帧率下连续运行至少 30 分钟；记录实际帧数、丢帧和重连；断开后能自动恢复 |
| 推理调度 | 预热 10 次后连续测量至少 200 个周期；处理最新帧；无无限队列；繁忙跳过可计数；模型只加载一次；本地关键路径 p95 小于采样周期 |
| 模型 | 使用冻结阈值和独立测试集；按任务报告逐类指标、样本量和失败样例；数值按基线表的必达/目标级别判定 |
| 转换一致性 | 各运行格式通过同一黄金集和任务专属容差；报告完整测试集精度漂移 |
| 性能 | 分别报告预处理、模型、后处理，以及采集到推理完成、云端 ACK、前端展示的 p50/p95；每项至少 200 个有效周期并说明缺失样本 |
| 资源 | 报告 CPU、NPU、内存、温度、磁盘增长和模型冷启动时间 |
| 上传 | 稳定网络连续尝试至少 300 条，以收到 ACK 的唯一记录数/应上传唯一记录数计算成功率且不低于 99%；断网 10 分钟并恢复后 5 分钟内完成补传；重复业务记录为 0 |
| 前端 | 真实流、对应证据、任务输出和状态可见；过期、离线、Mock 与真实数据明确区分 |
| 闭环 | 至少一条真实正常样例和一条经批准的故障数据或安全替代样例完成“相机到报告”全链路；替代物只计功能闭环 |

30 分钟是课程最低门槛；有条件时应做 2 小时以上稳定性测试。性能数字必须标明时钟来源和测量端点：仅模型执行时间不能写成采集到展示时延，视频 FPS 不能写成模型 FPS。

### 15.3 一票否决项

- 最终演示仍使用 Mock，却未在界面和报告中说明。
- 只用本地图片，没有老师提供的工业相机实测。
- 只在电脑运行模型，没有目标开发板实测。
- 测试集与训练集存在重复或相邻视频帧泄漏。
- 只展示总体指标，不报告核心故障类召回、任务专属逐类指标和失败样例。
- 模型转换后没有做各运行格式的黄金集一致性验证。
- 任务输出与证据帧不对应，却被描述为实时识别。
- 代码中包含密钥、明文密码、演示账号或真实上传数据。

## 十六、推荐阶段与分工

| 阶段 | 主要工作 | 阶段出口 |
| --- | --- | --- |
| 第 1 阶段：定义与清点 | 问题、类别、错误成本、硬件、SDK、板端工具链、接口草案 | 任务规范和硬件清单通过评审 |
| 第 2 阶段：数据与相机并行 | 数据来源/标注/切分；相机枚举/单帧/连续流 | 数据报告和相机 30 分钟报告 |
| 第 3 阶段：模型基线 | 冒烟训练、完整训练、逐类评测、错误分析 | 冻结候选模型与工作阈值 |
| 第 4 阶段：板端部署 | ONNX、板端转换、黄金集对齐、常驻推理服务 | 板端精度与性能报告 |
| 第 5 阶段：边云闭环 | 抽帧、outbox、上传、事件、数据库、前端 | 真实相机正常/故障闭环 |
| 第 6 阶段：故障与答辩 | 断线恢复、重复上传、稳定性、报告和演示预案 | 验收清单逐项有证据 |

五人小组可分别负责系统与契约、数据与模型、工业相机与边缘、云端与数据库、前端与测试。模型成员和相机/边缘成员必须共同维护模型交付包与黄金集，不能只通过口头传递输入尺寸和类别。

## 十七、最终交付物

最终成绩不应只看代码行数。每组至少交付：

- 任务定义、范围和类别规范。
- 经教师确认的验收基线表，含任务、数据、指标、样本量、性能协议和安全边界。
- 硬件与软件环境清单，含相机 SDK 和开发板版本。
- 数据集卡片、来源/许可/哈希、切分清单、类别分布和标注审查报告。
- 可复现实验记录、逐类模型评测、失败样例和阈值选择依据。
- 带哈希的模型包、预处理/后处理契约和黄金样例。
- ONNX 与板端模型转换记录、一致性和精度漂移报告。
- 工业相机连续采集、丢帧、参数、断线重连和成像质量报告。
- 边缘端端到端性能、资源占用和稳定性报告。
- 云端接口契约、数据模型、幂等/离线补传和安全说明。
- 前端真实状态截图或演示视频，以及完整系统测试报告。
- 一段从系统冷启动到真实闭环的演示录像和答辩说明。

每一项结论都应能回答“使用了什么版本和数据”“如何复现”“证据在哪里”“失败时系统怎样表现”。

## 十八、进一步优化方向

完成基本验收后，再考虑以下方向：

- 用现场误检和漏检做主动学习，持续扩充目标相机域数据。
- 采用量化、算子融合、零拷贝和流水线并行降低板端时延，但必须复测精度。
- 引入跟踪与事件级评估，减少同一故障重复告警。
- 建立模型注册、灰度发布、回滚和设备配置审计。
- 将本地图片存储升级为对象存储，将 SQLite 升级为服务型数据库。
- 增加可观测性，包括帧率、丢帧、队列、推理分位延迟、上传重试和温度趋势。
- 在具备足够现场数据后，再扩展更多设备、缺陷、分割、OCR 或多传感器融合。

优化的顺序应始终是：先补证据最薄弱的环节，再扩功能。一个能在真实相机、真实开发板、经批准的真实故障数据或安全替代链路上稳定运行并解释清楚的窄系统，比一个页面很多但依赖 Mock 的“大平台”更符合本课程目标。

## 结语

这份 README 只提供问题拆解、工程方向和验收标准，不替下一届同学做实现选择。请把 AI 当作设计、编码和排错工具，而不是结果真实性的替代品。课程最有价值的部分，是亲手把数据、模型、工业相机、边缘硬件和云端系统之间的每一个边界验证清楚。
